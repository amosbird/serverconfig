# Network Policy Routing Simplification Design

**Date:** 2026-07-31
**Status:** Approved

## Goal

Return the network stack to four explicit routing policies:

1. destinations listed by `addroutes` / `~/.routefile` leave through the physical network;
2. current LAN destinations leave through the current LAN;
3. Tencent intranet traffic uses IOA, including domain-derived destinations identified by SmartDNS;
4. all other traffic uses the selected Tailscale exit node.

IOA and Tailscale must remain independent tunnels. Each tunnel owns its own bootstrap, routing tables, marks, and recovery. Local policy selects business traffic between them but does not manage either tunnel's health.

The selected Tailscale exit node is intentionally fail-closed. If it is unavailable, default traffic may stop; local scripts must not detach it, bypass it, restart Tailscale, or silently leak default traffic to the physical network.

## Current Problems

The current reconciler accumulated responsibilities that belong to Tailscale and SmartGateAgent:

- it caches the global DERP address list and routes every relay through a local `underlay` table, despite Tailscale already marking its own transport traffic with `0x80000`;
- it guesses IOA bootstrap addresses from DNS and live SmartGateAgent sockets, then retains their union indefinitely;
- `network-fallback` changes the user's exit-node preference while Tailscale is attempting to recover;
- broad RFC1918 rules treat networks as local even when they are not connected;
- static `9.0.0.0/8` routing sends public space to IOA without sufficient evidence;
- the `ip` override silently reports success for every unrecognised `ip rule`, preventing SmartGateAgent from installing its own table 230 source rule;
- `NETMODE_IOA` can modify packets already marked by another owner.

This creates multiple sources of truth and makes AP changes affect tunnel internals that local policy should not own.

## Chosen Architecture

Use a small ordered `ip rule` policy. Keep the existing `cn` table name and ID 101 as the direct-route table; renaming it would add migration work without changing semantics.

The effective order is:

| Order | Match | Lookup/Action | Owner |
|---:|---|---|---|
| 1 | Tailscale-owned `0x80000/0xff0000` mark | `main` | Tailscale |
| 2 | current kernel `scope link` destinations, physical gateway, DHCP resolvers | `main` | networkd/kernel + reconciler |
| 3 | destinations in `~/.routefile` | `cn` via the physical gateway | reconciler |
| 4 | SmartGateAgent-owned `0xa38` mark | table `20` | SmartGateAgent |
| 5 | exact business mark `0x1` | table `ioa` | reconciler selects; SmartGateAgent owns table |
| 6 | `10.0.0.0/8` and `100.12.0.0/16` | table `ioa` | reconciler |
| 7 | tailnet `100.64.0.0/10` | table `52` | Tailscale |
| 8 | unmatched traffic | Tailscale's own exit-node rules | Tailscale |

The numeric preferences may differ from this ordinal list, but tests must enforce this ordering.

### Routefile Is Authoritative

`~/.routefile` is generated by `scripts/updateroutes` from APNIC's CN allocation list and consumed by the reconciler. A routefile destination always goes directly through the physical gateway, even if it overlaps an IOA static CIDR or has been added to SmartDNS's `ioa` ipset.

This is expressed by placing the single `lookup cn` rule before every IOA business rule. The `cn` table contains only the routefile prefixes and uses the current physical gateway.

### LAN Means Actually Connected

Only routes that currently exist as `scope link` in `main`, plus the current physical gateway and DHCP resolvers, bypass the tunnels.

Remove broad guesses for:

- `192.168.0.0/16`
- `172.16.0.0/12`
- `169.254.0.0/16`

A Docker, VM, wired, or wireless network is direct only while the kernel has a connected route for it. An unrelated private destination follows the normal default policy and therefore the exit node.

Gateway and DHCP resolver addresses remain explicit because a resolver can be public and because LAN ranges can overlap IOA's `10.0.0.0/8` policy.

### IOA Static and Domain-Derived Routing

Static IOA routing is:

- `10.0.0.0/8` after actual LAN and routefile rules;
- `100.12.0.0/16` after actual LAN and routefile rules.

`9.0.0.0/8` is not statically routed to IOA. It is public address space and there is insufficient evidence that the entire range is IOA intranet. A `9.x` destination can still use IOA when SmartDNS identifies it.

SmartDNS remains the owner of `ipset ioa`. `NETMODE_IOA` is the necessary bridge from SmartDNS's domain classification to policy routing:

1. packets with any existing non-zero mark are returned unchanged;
2. an unmarked packet is marked `0x1` only when its destination is in both `ipset ioa` and `ipset ioa_intranet`;
3. the `0x1` rule uses an exact full-width mask.

Conceptually:

```text
mark != 0
    -> RETURN

mark == 0
and destination in ipset ioa
and destination in ipset ioa_intranet
    -> set exact mark 0x1
```

`ioa_intranet` retains `9.0.0.0/8`, `10.0.0.0/8`, and `100.12.0.0/16`. This is a safety boundary for domain-derived classification, not a static routing declaration.

This preserves both tunnel owners' marks:

- Tailscale `0x80000` remains unchanged;
- SmartGateAgent `0xa38` remains unchanged;
- any other non-zero mark remains unchanged.

## Tunnel Ownership

### Tailscale

Tailscale exclusively owns:

- `tailscale0`;
- table `52` and its rules;
- mark `0x80000/0xff0000`;
- DERP, STUN, control-plane selection, and rebind;
- exit-node preference, health, and recovery.

The local policy keeps Tailscale's marked escape rule before business routing. It does not cache DERP IPs or create per-DERP routes.

The exit node is fail-closed. No local component calls `tailscale set --exit-node=`, `tailscale down/up`, or restarts `tailscaled` as recovery. Tailscale has demonstrated native link-change recovery on this machine: it detects a physical-interface loss, rebinds when `wlan0` returns, and restores the running exit-node path.

### SmartGateAgent

SmartGateAgent exclusively owns:

- `tun0`;
- table `20` and mark `0xa38`;
- table `230` and its source-address rule;
- physical gateway updates for tables `20` and `230`;
- creation and removal of the IOA tunnel route.

SmartGateAgent's observed native design has two physical escape paths:

```text
SO_MARK 2616 (0xa38) -> table 20 -> physical gateway
from <physical source address> -> table 230 -> physical gateway
```

The reconciler must not pin, deduplicate, validate, rebuild, or delete these rules or tables.

The `ip` override retains one deliberate intervention: SmartGateAgent's unqualified

```text
route add default via 192.168.255.1 dev tun0
```

is rewritten into table `ioa`, preventing IOA from replacing the global default route. All known table 20/230 route and rule lifecycle operations pass through unchanged. Unknown rule operations must not return a silent false success; they must execute normally or fail visibly according to the implementation plan.

Table `ioa` is therefore populated by SmartGateAgent through the override, while local policy decides which business traffic looks it up.

## Reconciler Responsibilities

`network-reconfigure` owns only:

- the current connected-LAN, physical gateway, and DHCP resolver bypass rules;
- the `cn` table loaded from `~/.routefile`;
- ordering the `cn`, IOA business, and tailnet policy rules;
- `ipset ioa_intranet`;
- the minimal `NETMODE_IOA` chain and exact business mark rule;
- SmartDNS DHCP and office fragments that depend on the physical link. The IOA resolver is
  permanently configured in the base SmartDNS config and never generated from `tun0` state.

SmartDNS always configures `192.168.255.10` in the excluded `ioa` group. When `tun0` is absent,
IOA names fail closed and may time out rather than using a public resolver; the default group remains
independent. The reconciler never generates an IOA DNS fragment or restarts SmartDNS for `tun0`
down/up or address changes.

On AP or DHCP changes it updates only those objects. It does not react to `tailscale0` or `tun0` as routing-change inputs and does not operate tables `20`, `230`, `52`, or Tailscale preferences.

Retain add-before-delete reconciliation and compare desired and actual owned rules in both directions. These mechanisms prevent empty-rule windows and remove foreign rules from owned priority bands without requiring a destructive global reset.

## Components Removed

Remove all code, state, documentation, deployment, and rollback handling for:

- `scripts/network-fallback`;
- `network/systemd/network-fallback.service`;
- `/var/lib/network-fallback`;
- DERP map collection and `/var/lib/network-reconfigure/derp-ips`;
- IOA bootstrap hostname guesses;
- SmartGateAgent socket scanning;
- `/var/lib/network-reconfigure/ioa-endpoints`;
- the `underlay` and staging tables once no remaining policy uses them;
- broad RFC1918 and link-local direct rules;
- static `9.0.0.0/8 -> ioa` routing;
- reconciler ownership of the `0xa38` rule and table `20` consistency checks.

Update `netfix` and `network-status` rather than leaving checks for removed architecture.

## Failure Semantics

- If the physical network is absent, all external traffic can fail.
- If the selected Tailscale exit node is unavailable, unmatched/default traffic fails closed until Tailscale recovers it.
- LAN, routefile, and IOA traffic continue according to their explicit higher-priority policies when their own paths are available.
- If IOA is absent, table `ioa` is empty and IOA lookups fall through to later rules; the reconciler does not infer IOA liveness.
- If SmartDNS misclassifies a public IOA-related hostname, the destination must also belong to `ioa_intranet` before it can receive the IOA business mark.
- A reconciler failure must not alter either tunnel's preferences or owner-managed tables.

## AP Change Data Flow

On a physical link or DHCP change:

1. networkd establishes the connected routes, physical gateway, and lease;
2. `network-reconfigure.path` triggers the reconciler;
3. the reconciler reads current `scope link` routes, physical gateway, and DHCP resolvers;
4. it updates SmartDNS's DHCP fragment;
5. it rebuilds `cn` only when its physical gateway changed or the table is missing;
6. it reconciles only its owned policy bands and minimal IOA marking chain;
7. Tailscale independently receives the kernel link event and performs its own rebind;
8. SmartGateAgent independently updates tables `20` and `230` and its tunnel.

No local hook coordinates or restarts the tunnels.

## Verification Design

All destructive verification runs in a network namespace. Live verification remains read-only.

### Policy Ordering

Tests must prove:

- an actual connected LAN inside `10.0.0.0/8` uses `main`, not IOA;
- a routefile prefix overrides static `10.0.0.0/8` and `100.12.0.0/16` IOA routing;
- a routefile prefix overrides an exact `0x1` business mark;
- a non-connected RFC1918 destination is not forced to `main`;
- `100.64.0.0/10` uses table `52`;
- unmatched traffic is not given a local main-table bypass.

### Mark Isolation

Tests must pass packets through `NETMODE_IOA` and prove:

- mark `0` plus both ipsets becomes exactly `0x1`;
- mark `0` missing either ipset remains `0`;
- `0xa38` remains `0xa38`;
- `0x80000` remains `0x80000`;
- an arbitrary non-zero mark remains unchanged;
- the exact `0x1` rule does not match `0xa39` or another mark whose low bit is one.

### Override Contract

Use a fake `/usr/bin/ip` target or an extracted command-transform function to prove:

- the unqualified IOA default is rewritten to `table ioa`;
- add/delete of `fwmark 2616 table 20` passes unchanged;
- add/delete of `from <IPv4> table 230` passes unchanged;
- route add/flush for tables `20` and `230` passes unchanged;
- unknown rules are not silently reported as successful no-ops.

### Ownership and Roaming

Tests must prove:

- an AP change updates connected LAN, gateway, DHCP resolvers, and `cn` gateway;
- stale rules and old `cn` gateways are removed;
- tables `20`, `230`, and `52` are byte-for-byte unchanged by the reconciler;
- no code path invokes Tailscale preference, down/up, or restart commands;
- cold boot from empty owned tables and rules converges without relying on tunnel-owned state.

### Deletion Checks

Static checks must fail if the resulting tree still contains active references to:

- DERP caches or route generation;
- IOA endpoint caches or bootstrap hostname guesses;
- `network-fallback`;
- broad RFC1918 direct rules;
- static `9.0.0.0/8 -> ioa`;
- reconciler manipulation of table `20`, table `230`, or exit-node preferences.

## Migration and Rollback

Migration removes the fallback service and obsolete state, flushes obsolete underlay/staging tables, then runs the simplified reconciler. It must not stop Tailscale, SmartDNS, or SmartGateAgent on the live machine.

Rollback/removal code must clear only objects this repository owns. It must not flush SmartGateAgent tables `20`, `230`, or `ioa`, and must not alter Tailscale table `52` or exit-node preferences.

The implementation is complete only after namespace tests pass, mutation checks demonstrate that the new assertions can fail, shell syntax/static checks pass, and a live read-only report confirms the intended route decisions.
